# Diagnosing dynamic navigation

Start navigation, enter a goal, then expand **Local route tools** and enable **Show route debug inspector**. Enabling or disabling the inspector changes its presentation only; planning and verification use the same bounded evidence either way. No diagnostic telemetry is sent.

The live inspector shows the current observation revision, structure/state fingerprints and partial-scan status. Its candidate table explains label, description and context matches, qualifier/preference rejection, disabled or consequential controls, hidden targets, reveal ownership and ambiguity. A selected opening control can have a low goal score because it is a grounded reveal step for the actual target. Scores rank evidence and are not measured accuracy percentages. Labels are displayed only if the current document binding still matches the recorded signature.

Memory evidence records the site/page versions, age in seconds, counts of inferred/observed transitions and the actual observed path used by a remembered route. Inferred links are not promoted to verified routes. The verification history distinguishes a user interaction from its observed result: checked changes, focus, section arrival, menu expansion and destination arrival. Stale bindings, timeouts and canceled guidance have separate records. Up to thirty events survive ordinary same-origin page loads; temporary control IDs are specific to a document.

**Export diagnostics** produces a local `navigator-live-debug-v1` JSON report. Reports include up to fifty ranked candidates and thirty events. They contain hashed identities, enums, booleans and numeric scoring evidence, with no page labels, descriptions, goal text, URLs/paths, DOM, field values or model text. Unknown role strings are replaced by `unknown`. The strict report schema rejects extra fields and arbitrary rejection/event text. Fingerprints are correlation aids, not cryptographic anonymization.

For each candidate, the semantic score can be reproduced from `evidence`: when `qualified`, `preference` and a nonzero `requested` count hold, clamp `weighted / requested - specificity + adjustment` into 0–1. Otherwise it is zero. Subtract the 0.06 hidden-target cost and clamp at zero. Eligibility also requires enabled/ordinary-risk status, visibility or one usable revealer, and a score of at least 0.6. Candidates within 0.08 of the best eligible score are compared by their hashed identity; different identities cause ambiguity. Model and memory sources are identified separately. Truncated reports cannot reconstruct candidates beyond the retained bound.

A report reproduces the recorded ranking/verification evidence rather than an entire website. To reproduce a browser failure, retain the extension version, viewport, public test URL and user action sequence in the issue separately, and add a minimal sanitized fixture to the test suite. Never export a raw DOM or real field contents to create a fixture.

Regression coverage is in `tests/live-diagnostics.test.ts` and `tests/e2e/live-navigation.spec.ts`, including language-versus-Tools reasoning, score replay, bounded reports, forged text rejection, memory provenance, privacy sentinels, inspector toggling and verification history across a page load.
